**DaemonSet** — это ресурс (API-объект) в Kubernetes, который используется для управления подами, предоставляющими возможности уровня узла.

DaemonSet гарантирует, что на всех (или некоторых) узлах кластера запущена копия определенного пода. Когда в кластер добавляется новый узел, DaemonSet автоматически добавляет на него нужный под. Когда узел удаляется, эти поды также удаляются (сборщиком мусора). Удаление DaemonSet приведет к очистке всех созданных им подов.

### Основные сценарии использования

DaemonSet идеально подходит для задач, которые должны выполняться на каждом узле кластера. Типичные примеры:

*   **Сбор логов**: запуск на каждом узле агента (например, Fluentd, Filebeat), который собирает логи контейнеров с этого узла и отправляет их в централизованное хранилище.
*   **Мониторинг**: запуск агентов для сбора метрик с узла и запущенных на нем подов (например, Prometheus Node Exporter).
*   **Сетевые плагины (CNI)**: многие сетевые решения (Calico, Weave) запускают свои компоненты на каждом узле для настройки сетевых правил.
*   **Хранилище (Storage)**: демоны для управления доступом к внешним томам, которые должны присутствовать на каждом узле.
*   **Безопасность и аудит**: инструменты для проверки безопасности контейнеров или агенты для контроля доступа (например, Falco).

### Как работают поды DaemonSet

Процесс управления DaemonSet выглядит следующим образом:

1.  **Создание**: администратор создает манифест DaemonSet (YAML), в котором описывается шаблон пода, селектор и другие параметры.
2.  **Назначение на узлы**: встроенная в Kubernetes логика управления DaemonSet (реализованная в `kube-controller-manager`) отслеживает состояние узлов. Для каждого узла, который соответствует условиям (например, меткам `nodeSelector` или правилам affinity), она автоматически создает под. При этом под получает специальную настройку `nodeAffinity`, которая жестко привязывает его к конкретному узлу. Стандартный планировщик (scheduler) фактически не участвует в выборе узла.
3.  **Запуск**: kubelet на целевом узле получает задание и запускает под.
4.  **Обновление**: при изменении шаблона пода в DaemonSet (например, обновлении версии образа), можно выполнить постепенное обновление (rolling update) подов на узлах.

### Запись манифеста DaemonSet (YAML)

DaemonSet описывается в YAML-файле. Рассмотрим его структуру на примере из документации для агента сбора логов `fluentd`:

```yaml
apiVersion: apps/v1
kind: DaemonSet                # 1. Тип ресурса
metadata:
  name: fluentd-elasticsearch
  namespace: kube-system
spec:
  selector:                    # 2. Селектор подов
    matchLabels:
      name: fluentd-elasticsearch
  template:                    # 3. Шаблон пода
    metadata:
      labels:                  # Метки должны совпадать с селектором
        name: fluentd-elasticsearch
    spec:
      tolerations:             # 4. Допуски (toleration)
      - key: node-role.kubernetes.io/control-plane
        operator: Exists
        effect: NoSchedule
      containers:
      - name: fluentd-elasticsearch
        image: quay.io/fluentd_elasticsearch/fluentd:v5.0.1
        resources:
          limits:
            memory: 200Mi
          requests:
            cpu: 100m
            memory: 200Mi
        volumeMounts:
        - name: varlog
          mountPath: /var/log
      volumes:
      - name: varlog
        hostPath:              # 5. Использование файловой системы узла
          path: /var/log
```

**Ключевые поля:**

1.  **`kind: DaemonSet`**: определяет тип ресурса.
2.  **`.spec.selector`**: селектор, который используется, чтобы DaemonSet "видел" созданные им поды. Он должен соответствовать меткам в шаблоне пода. Это поле нельзя изменить после создания.
3.  **`.spec.template`**: шаблон пода, который будет запускаться. Содержит стандартное описание пода.
4.  **`tolerations` (допуски)**: в примере выше они позволяют запускать поды на управляющих узлах (control plane), которые обычно имеют отметку `NoSchedule`.
5.  **`volumes` с `hostPath`**: часто используется для предоставления поду доступа к файловой системе узла (например, к директории с логами `/var/log`).

### Запуск подов на выбранных узлах

По умолчанию поды DaemonSet запускаются на **всех** узлах кластера. Чтобы ограничить запуск только определенными узлами, используются стандартные механизмы назначения подов на узлы:

*   **`nodeSelector`**: самый простой способ. В `.spec.template.spec` добавляется `nodeSelector` с метками, которым должны соответствовать узлы.
*   **`affinity` (правила сходства)**: более гибкий способ, позволяющий задавать сложные правила (например, `preferredDuringSchedulingIgnoredDuringExecution`).

### Взаимодействие с подами DaemonSet

Существует несколько паттернов для взаимодействия с подами, управляемыми DaemonSet:

*   **Push (отправка)**: поды сами отправляют данные (например, метрики или логи) во внешнюю систему. Клиенты для прямого обращения к ним не требуются.
*   **NodeIP и известный порт**: поды используют `hostPort`, и становятся доступны по IP-адресу узла и заранее известному порту.
*   **DNS**: создается headless-сервис с тем же селектором, что и у DaemonSet. Тогда клиенты могут получать IP-адреса всех подов через DNS-запросы.
*   **Service (сервис)**: создается обычный сервис с тем же селектором, который распределяет трафик между подами DaemonSet.

### Обновление DaemonSet

Обновление подов в DaemonSet (например, смена версии образа) выполняется через изменение его манифеста. Стратегия обновления (`updateStrategy`) по умолчанию — `RollingUpdate`, что позволяет обновлять поды постепенно, с возможностью контроля за процессом.

### Альтернативы DaemonSet

В документации также рассматриваются альтернативные подходы:

*   **Init-скрипты или systemd**: запуск демонов напрямую на узле. Минус — потеря интеграции с инструментами Kubernetes (мониторинг, управление).
*   **Обычные поды (Bare Pods)**: можно создать под и указать ему конкретный узел через `nodeName`. Однако DaemonSet автоматически восстановит под, если он будет удален или узел выйдет из строя.
*   **Статические поды (Static Pods)**: поды, создаваемые kubelet'ом из файлов манифеста на самом узле. Они не управляются через API-сервер и используются в основном для компонентов control plane.
*   **Deployment**: используется для запуска нескольких копий приложения, где не важна привязка к конкретному узлу. DaemonSet же гарантирует наличие ровно одной копии на определенных узлах.

### Резюме

**DaemonSet** — это стандартный и предпочтительный способ развертывания в Kubernetes системных или инфраструктурных компонентов, которые должны присутствовать на каждом узле кластера. Он гарантирует, что на каждом подходящем узле будет запущен нужный под, и автоматически поддерживает это состояние при изменении состава узлов.
