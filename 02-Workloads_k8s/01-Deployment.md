**Deployment** — это один из самых популярных и фундаментальных типов ресурсов  в Kubernetes. Если Pod — это «лошадка», которая запускает ваш код, то Deployment — это **наездник**, который управляет этой лошадкой: говорит, сколько их должно быть, как их обновлять и что делать, если лошадка упала.

**Deployment** — это объект Kubernetes, предназначенный для управления жизненным циклом приложений путем автоматического развертывания, масштабирования и обновления контейнеризированных приложений.

Простыми словами: **Deployment описывает желаемое состояние приложения.**

Давай разберем его по полочкам.

### 1. Зачем нужен Deployment (если есть Pod)?

Создать просто Pod можно, но это не практично для продакшена. Если Pod упадет (закончится память, упадет нода), он исчезнет навсегда. Deployment же создает Pod-ы и следит, чтобы они жили. Он опирается на другой ресурс — **ReplicaSet** (который отвечает за поддержание нужного количества копий), но предоставляет поверх этого гораздо более мощные возможности.

Deployment нужен для:
*   **Масштабирование** (Scaling): Легко увеличить или уменьшить количество копий приложения.
*   **Обновления без простоя** (Rolling Updates): Обновить версию приложения так, чтобы пользователи не заметили перерыва в работе.
*   **Откат** (Rollback): Если новая версия сломалась, быстро вернуться к старой стабильной.
*   **Самовосстановление** (Self-healing): Если Pod упал, Deployment создаст новый.

### 2. Как выглядит Deployment (YAML)

Создадим файл `my-deployment.yaml`:

```yaml
apiVersion: apps/v1  # Версия API (для Deployment она всегда apps/v1)
kind: Deployment      # Тип ресурса
metadata:
  name: my-app        # Имя нашего деплоймента
  labels:
    app: my-app
spec:
  replicas: 3         # Сколько копий (подов) должно быть всегда запущено
  selector:
    matchLabels:
      app: my-app     # Этот deployment будет следить за подами с меткой app: my-app
  template:           # Шаблон пода (как будет выглядеть Pod, который создаст этот Deployment)
    metadata:
      labels:
        app: my-app   # Метка пода (должна совпадать с selector)
    spec:
      containers:
      - name: my-container
        image: nginx:latest  # Какой образ Docker использовать
        ports:
        - containerPort: 80
```

**Структура:**
1.  **`metadata`**: Имя деплоймента.
2.  **`spec.replicas`**: Желаемое количество реплик.
3.  **`spec.selector`**: Как деплоймент находит свои поды (по меткам).
4.  **`spec.template`**: Это самое важное — это описание того Pod, который будет создан. Если ты умеешь создавать Pod, ты уже знаешь, что писать внутри `template.spec`.

### 3. Как это работает под капотом?

Когда ты создаешь Deployment (`kubectl apply -f my-deployment.yaml`), происходит цепочка:
1.  **Deployment** создает **ReplicaSet**.
2.  **ReplicaSet** создает указанное количество **Pod**.
3.  **Pod** запускают контейнеры.

Если ты обновишь образ (например, с `nginx:latest` на `nginx:1.25`), Deployment создаст **новый ReplicaSet** с новыми подами и плавно остановит старые (Rolling Update).

### 4. Основные стратегии обновления

В Deployment есть два основных режима обновления:

*   **RollingUpdate (по умолчанию):**
    *   Обновление происходит частями.
    *   Kubernetes постепенно заменяет старые Pod-ы новыми.
    *   Во время обновления у тебя одновременно работают и старая, и новая версии (но сервис всегда онлайн).
    *   Можно настроить параметры `maxSurge` (на сколько можно превысить количество подов во время апдейта) и `maxUnavailable` (сколько подов может быть недоступно).

*   **Recreate:**
    *   Сначала **удаляются все старые** Pod-ы.
    *   **Потом создаются новые**.
    *   Это приводит к **простою** (даунтайму). Используется редко, только если приложение не умеет работать в две версии одновременно (например, при работе с шедулерами или монолитными базами данных).

### 5. Полезные команды (kubectl)

Зная, что у тебя есть Deployment `my-app`, ты можешь:

1.  **Создать/применить деплоймент:**
    ```bash
    kubectl apply -f my-deployment.yaml
    ```

2.  **Посмотреть список деплойментов:**
    ```bash
    kubectl get deployments
    # или подробно
    kubectl get deployments -o wide
    ```

3.  **Посмотреть статус обновления:**
    ```bash
    kubectl rollout status deployment/my-app
    ```

4.  **Изменить образ (например, на новую версию):**
    ```bash
    kubectl set image deployment/my-app my-container=nginx:1.25
    # my-container - имя контейнера в шаблоне, nginx:1.25 - новый образ
    ```

5.  **Масштабировать приложение до 5 копий:**
    ```bash
    kubectl scale deployment/my-app --replicas=5
    ```

6.  **Посмотреть историю изменений (версии):**
    ```bash
    kubectl rollout history deployment/my-app
    ```

7.  **Откатиться к предыдущей версии:**
    ```bash
    kubectl rollout undo deployment/my-app
    ```

8.  **Откатиться к конкретной версии (revision):**
    ```bash
    kubectl rollout undo deployment/my-app --to-revision=2
    ```

### 6. Когда использовать Deployment?

Deployment — это стандарт де-факто для большинства *stateless* (без сохранения состояния) приложений.
*   Веб-сервера (Nginx, Apache)
*   Бэкенд-приложения (Python, Go, Java, Node.js)
*   Микросервисы

**Когда Deployment НЕ подходит (или нужен не только он):**
*   **StatefulSet**: Если твоему приложению нужны уникальные идентификаторы, стабильные имена и persistent storage (базы данных, кластеры типа Kafka, Cassandra). Для них есть отдельный ресурс — StatefulSet.
*   **DaemonSet**: Если нужно, чтобы под был запущен **на каждом узле** кластера (например, агенты мониторинга, логгирования). Для этого есть DaemonSet.
*   **Job / CronJob**: Если нужно выполнить код один раз и завершиться (разовая задача или по расписанию).

### Резюме
**Deployment** — это "умный менеджер" для твоих подов. Ты говоришь ему: "Хочу 3 копии Nginx последней версии", — а он сам следит, чтобы это желание всегда исполнялось, даже если что-то пошло не так.
