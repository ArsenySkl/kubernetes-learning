Давай разберем **Container Runtime** — один из ключевых компонентов **Data Plane** (плоскости данных) в Kubernetes.

Если объяснять максимально просто: **Container Runtime — это программа, которая непосредственно запускает и управляет контейнерами на узле (Node).** Без него поды с контейнерами были бы просто набором файлов на диске.

### 1. Место в архитектуре: Data Plane vs Control Plane

Чтобы понять роль Container Runtime, нужно вспомнить логическое разделение кластера Kubernetes:

*   **Control Plane (Плоскость управления):** «Мозг» кластера. Принимает решения, обрабатывает запросы (`kubectl apply`), хранит состояние в etcd, планирует поды. Компоненты: `kube-apiserver`, `etcd`, `kube-scheduler`, `kube-controller-manager`.
*   **Data Plane (Плоскость данных):** «Мышцы» и «исполнители». Несет нагрузку, выполняет команды, запускает приложения. Находится на каждом рабочем узле (Node). Компоненты:
    1.  **kubelet:** Главный агент на узле. Он общается с Control Plane, получает задание запустить под и говорит: «Эй, Container Runtime, создай контейнер с образом nginx».
    2.  **Container Runtime:** Непосредственно создает, останавливает и удаляет контейнеры.
    3.  **kube-proxy:** Отвечает за сетевые правила.

**Резюме:** Control Plane решает, *что* запустить, а Data Plane (в лице kubelet и Container Runtime) — *как* это сделать физически.

### 2. Что делает Container Runtime?

Это низкоуровневый компонент, который выполняет грязную работу по изоляции процессов. Его задачи:

1.  **Pull образов:** Скачивает Docker-образ (например, `nginx:latest`) из registry (репозитория) по запросу kubelet'а.
2.  **Создание контейнера:** Распаковывает образ, использует системные вызовы ядра Linux (namespaces, cgroups, chroot), чтобы создать изолированную среду для процесса.
3.  **Запуск/Остановка процессов:** Запускает главный процесс (PID 1) внутри контейнера.
4.  **Управление ресурсами:** Ограничивает потребление CPU, RAM и диска согласно настройкам пода (requests/limits) с помощью `cgroups`.
5.  **Сбор логов и метрик:** Перенаправляет потоки stdout/stderr контейнера, чтобы их мог прочитать kubelet, а затем передать в систему логирования.
6.  **Мониторинг жизнеспособности:** Runtime сообщает kubelet'у, жив ли процесс (для проверок liveness/readiness probes).

### 3. Эволюция: Docker, CRI и замена Docker'а

Раньше всё было просто: Kubernetes работал напрямую с Docker. Docker был единственной "печкой", от которой плясали.

**Проблема:** Если Kubernetes завязан на Docker, его сложно заменить на что-то другое (например, на более легкие решения). Чтобы решить эту проблему, придумали стандарт.

#### CRI (Container Runtime Interface)
Это стандартный API (интерфейс), который Kubernetes (а именно kubelet) использует для общения с любым runtime'ом. Это как универсальный USB-разъем.
*   Если runtime поддерживает CRI, kubelet может управлять им, не зная его внутренней кухни.

#### Удаление Docker (Dockershim)
Docker сам по себе не поддерживал CRI из коробки. Поэтому в Kubernetes был специальный костыль — `dockershim`, который переводил команды kubelet'а на язык Docker.
В версии Kubernetes 1.24 `dockershim` удалили. Теперь, если вы хотите использовать Docker на узлах, вам нужен переходник (например, `cri-dockerd`). Но чаще всего сейчас используют runtime'ы, которые изначально спроектированы под CRI.

### 4. Основные виды Container Runtime

Их можно разделить на два уровня: высокоуровневые (используют containerd) и низкоуровневые (запускают контейнеры по-настоящему).

1.  **containerd (самый популярный):**
    *   Промышленный стандарт. Раньше был частью Docker, но потом выделился в独立ный проект и вступил в CNCF.
    *   Поддерживает CRI из коробки (через плагин).
    *   Используется по умолчанию в большинстве managed Kubernetes (например, GKE, EKS с настройками по умолчанию).

2.  **CRI-O:**
    *   Специально создан Red Hat специально для Kubernetes как легковесная альтернатива.
    *   Не делает ничего лишнего — только то, что нужно CRI.
    *   Используется в OpenShift.

3.  **Docker (через cri-dockerd):**
    *   Используется там, где нужна обратная совместимость или разработчики привыкли к тулчейну Docker. Но для продакшена обычно стараются уходить на containerd.

4.  **Низкоуровневые:**
    *   **runc:** То, что *на самом деле* запускает контейнеры (и containerd, и CRI-O, и Docker используют его внутри). Работает на основе стандарта OCI (Open Container Initiative).
    *   **Kata Containers / gVisor:** Это рантаймы для повышенной безопасности. Они создают виртуальную легкую машину вокруг контейнера, чтобы ядро хоста и ядро контейнера были изолированы надежнее, чем стандартные namespaces.

### Схема взаимодействия Data Plane

Вот как выглядит цепочка вызова на узле:

1.  **kubelet:** «Эй, CRI, мне нужен новый под с контейнером nginx».
2.  **CRI (containerd):** «Окей, сейчас... Эй, runc, создай контейнер на основе образа nginx, ограничь ему память и изолируй».
3.  **runc:** «Сделано. Процесс запущен, PID 1234 изолирован».
4.  **CRI (containerd):** «kubelet, контейнер готов, вот его статус».

### Итог

**Container Runtime** — это "двигатель" Data Plane в Kubernetes. Это компонент, который делает контейнеры контейнерами, используя возможности ядра Linux для изоляции процессов. Он скрыт от глаз пользователя, но без него ваше приложение никогда не запустилось бы.

В современных кластерах стандартом де-факто является **containerd** из-за его производительности, простоты и нативной поддержки CRI.

`он устанавливается вместе с дистрибутивом kubernetes или через плейбуки\другие способы инсталляции kubernetes?`

Отличный и важный вопрос! Он позволяет понять разницу между компонентами Kubernetes и тем, как они реально живут на сервере.

Короткий ответ: **Container Runtime НЕ входит в дистрибутив Kubernetes и не устанавливается автоматически вместе с ним.** Это независимый компонент, который необходимо установить и настроить отдельно — вручную или с помощью инструментов автоматизации .

Давай разберем подробнее, как это работает на практике.

### Почему Runtime — это отдельная история?

Вспомни архитектуру, которую мы обсуждали. Kubernetes (через компонент `kubelet`) только *управляет* контейнерами, но сам он их не запускает. Запуск — это задача специализированного инструмента — Container Runtime. Поэтому их жизненные циклы разделены.

*   **Пакеты Kubernetes** (`kubeadm`, `kubelet`, `kubectl`) — это "оркестратор". Они ставятся из своих официальных репозиториев (раньше `apt.kubernetes.io`, теперь `pkgs.k8s.io`) .
*   **Container Runtime** (например, `containerd`) — это "двигатель". Он ставится из своих собственных репозиториев (например, репозиториев Docker) или из стандартных репозиториев ОС .

Единственная "связка" — это то, что `kubelet` умеет искать runtime по определенным сокетам (например, `unix:///var/run/containerd/containerd.sock`), но сам его не ставит .

### Как это выглядит на практике: ручная установка

При ручной установке с использованием `kubeadm` процесс выглядит так:

1.  **Подготовка системы:** Отключается swap, загружаются модули ядра (`overlay`, `br_netfilter`) .
2.  **Установка Runtime:** Устанавливается и настраивается `containerd` (или другой runtime). Это отдельный шаг .
3.  **Установка Kubernetes:** Устанавливаются пакеты `kubeadm`, `kubelet`, `kubectl` .
4.  **Инициализация:** Запускается `kubeadm init`, который проверяет наличие работающего runtime на узле .

Вот пример команд для Ubuntu, которые наглядно показывают разделение (упрощенно) :

```bash
# 1. Устанавливаем Container Runtime (containerd)
sudo apt install -y containerd
# ... (дальше идет его настройка) ...

# 2. Добавляем репозиторий Kubernetes и устанавливаем его компоненты
sudo apt-get install -y kubelet kubeadm kubectl
sudo apt-mark hold kubelet kubeadm kubectl
```

### Автоматизация установки (Плейбуки Ansible)

Это самый распространенный способ в продакшене. Здесь логика та же, просто она записана в виде кода. В плейбуках Ansible этапы установки runtime и Kubernetes четко разделены на разные задачи .

**Пример структуры плейбука (из найденных примеров)** :

```yaml
# Задачи по установке Container Runtime (containerd)
- name: Install containerd
  ansible.builtin.package:
    name: containerd
    state: present

- name: Create containerd configuration directory
  ansible.builtin.file:
    path: /etc/containerd
    state: directory

# ... (дальше настройка containerd) ...

# --- Разделитель ---

# Задачи по установке Kubernetes
- name: Download Kubernetes GPG key
  ansible.builtin.get_url:
    url: "https://pkgs.k8s.io/core:/stable:/v{{ k8s_version }}/deb/Release.key"
    # ...

- name: Add Kubernetes APT repository
  ansible.builtin.apt_repository:
    repo: "deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/... /"
    # ...

- name: Install Kubernetes packages (kubelet, kubeadm, kubectl)
  ansible.builtin.apt:
    name:
      - "kubelet={{ k8s_package_version }}"
      - "kubeadm={{ k8s_package_version }}"
      - "kubectl={{ k8s_package_version }}"
```

### Что касается Managed Kubernetes (GKE, EKS, AKS)?

В облачных сервисах (Google Kubernetes Engine, Amazon EKS, Яндекс Managed Service for Kubernetes и др.) этот процесс скрыт от пользователя. Провайдер сам решает, какой runtime использовать (почти всегда это `containerd`), и устанавливает его на узлы автоматически при их создании. Вам не нужно думать об этом.

### Итог

*   **Container Runtime — это зависимость, а не компонент дистрибутива.** Kubernetes требует его наличия на узле, как требует наличия процессора и памяти.
*   При ручной установке или через плейбуки вы **всегда устанавливаете runtime отдельным, явным шагом**.
*   Инструменты вроде `kubeadm` только проверяют, что runtime уже есть и работает, но не ставят его .
