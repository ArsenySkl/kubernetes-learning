ikube-apiserver — это главный компонент control plane в Kubernetes, который можно назвать "входными воротами" или "мозгом" всего кластера . Это единственный компонент, с которым напрямую взаимодействуют все остальные части системы, будь то пользователь с `kubectl`, внутренние контроллеры или рабочие узлы .

Главная задача `kube-apiserver` — предоставлять RESTful API для управления кластером. Он получает все запросы на создание, изменение, удаление или получение информации об объектах (подах, сервисах, деплойментах и т.д.), обрабатывает их и сохраняет итоговое состояние в распределенное хранилище `etcd` . По сути, `kube-apiserver` — единственный компонент, который общается с `etcd` .

### Основные функции kube-apiserver

Работу `kube-apiserver` можно представить как многоступенчатую проверку и обработку каждого запроса, прежде чем он будет выполнен.

1.  **Аутентификация (Authentication)**. Первым делом сервер проверяет, кто именно отправляет запрос. Он поддерживает множество механизмов аутентификации, которые могут быть включены одновременно :
    *   **Клиентские сертификаты (TLS)**: наиболее распространенный способ для компонентов кластера.
    *   **Токены**: статические токены, `ServiceAccount` токены для подов, `BootstrapToken` для присоединения узлов.
    *   **Basic Auth**: аутентификация по логину и паролю (менее безопасна, не рекомендуется).
    *   **OpenID Connect (OIDC)**: интеграция с внешними провайдерами идентификации (например, Google, Okta).
    *   **Webhook Token**: делегирование проверки токена внешнему сервису.
    *   **Anonymous**: доступ для анонимных запросов.

2.  **Авторизация (Authorization)**. После того как личность установлена, сервер проверяет, есть ли у этого пользователя права на выполнение запрашиваемого действия (например, создавать поды в определенном пространстве имен). Основные механизмы авторизации :
    *   **RBAC (Role-Based Access Control)**: самый гибкий и распространенный способ, где права определяются ролями.
    *   **ABAC (Attribute-Based Access Control)**: доступ на основе атрибутов пользователя, ресурса и окружения.
    *   **Node**: специальный режим для авторизации запросов от `kubelet`.
    *   **Webhook**: делегирование проверки прав внешнему сервису.

3.  **Admission Control**. Это финальная стадия проверки перед сохранением объекта. Admission контроллеры — это специальные плагины, которые могут изменять (mutating) или отклонять (validating) запросы . Они проверяют запрос на соответствие политикам кластера. Примеры:
    *   `ResourceQuota`: проверяет, не превысит ли создаваемый объект квоты ресурсов в пространстве имен.
    *   `LimitRanger`: устанавливает лимиты по умолчанию для подов, если они не указаны.
    *   `NamespaceLifecycle`: запрещает создание объектов в удаляемых или несуществующих пространствах имен.
    *   `PodSecurity`: применяет политики безопасности к подам.

### Как kube-apiserver взаимодействует с другими компонентами

`kube-apiserver` — это коммуникационный хаб. Взаимодействие происходит через API, и многие компоненты используют механизм **watch**, чтобы отслеживать изменения .

1.  **С хранилищем (`etcd`)**: это единственный компонент, который напрямую читает и записывает данные в `etcd`. При этом `kube-apiserver` не нужно знать, какой из узлов `etcd` является лидером. Если запрос требует записи (и, соответственно, консенсуса), `kube-apiserver` отправляет его любому узлу `etcd`. Если узел не лидер, он автоматически перенаправит запрос лидеру. Чтение же может быть выполнено любым узлом .
2.  **С планировщиком (`kube-scheduler`)**: планировщик "следит" через API за новыми подами, которым не назначен узел. Когда он находит такой под, он принимает решение и через API сообщает `kube-apiserver` обновленный статус пода с указанием узла .
3.  **С контроллерами (`kube-controller-manager`)**: различные контроллеры (например, `Deployment` или `ReplicaSet`) следят за состоянием объектов. Если текущее состояние не соответствует желаемому (например, меньше подов, чем нужно), контроллер через API дает команду `kube-apiserver` создать недостающие объекты .
4.  **С рабочими узлами (`kubelet`)**: агент `kubelet` на каждом узле постоянно следит через API за тем, какие поды должны быть запущены именно на его узле. Когда появляется задание, `kubelet` запускает контейнеры и через API регулярно отправляет `kube-apiserver` отчеты о состоянии подов и самого узла .

### Особенности архитектуры

*   **Горизонтальное масштабирование**: `kube-apiserver` спроектирован так, чтобы легко масштабироваться. Для обеспечения высокой доступности (High Availability) можно запустить несколько экземпляров `kube-apiserver` и балансировать трафик между ними .
*   **Топологии HA**: в высокодоступных кластерах `kube-apiserver` работает в паре с `etcd` по одной из двух схем :
    *   **Совмещенная топология (Stacked etcd)**: `etcd` и `kube-apiserver` работают на одних и тех же узлах. Каждый `kube-apiserver` общается со своим локальным `etcd`. Это проще в установке.
    *   **Внешняя топология (External etcd)**: кластер `etcd` работает на выделенных узлах, отдельно от узлов с `kube-apiserver`. Это сложнее, но надежнее, так как отказ control plane узла не влияет напрямую на хранилище данных.

### Внутреннее устройство: три сервера в одном

Технически `kube-apiserver` внутри состоит из трех логических серверов, которые работают вместе, используя паттерн "делегирование" :

1.  **`AggregatorServer`**: отвечает за **агрегацию API**. Он позволяет подключать к основному API сторонние сервисы и расширения. Работает как прокси, перенаправляя запросы к соответствующим бэкендам.
2.  **`KubeAPIServer`**: ядро, которое предоставляет API для всех **встроенных ресурсов** Kubernetes (поды, сервисы, деплойменты и т.д.).
3.  **`APIExtensionsServer`**: отвечает за работу с **пользовательскими ресурсами (CRD)**. Он позволяет динамически регистрировать и обслуживать API для новых типов объектов, определяемых пользователем.

### Схема работы запроса на примере создания Pod

Чтобы лучше понять роль `kube-apiserver`, проследим путь команды на создание пода :
1.  Пользователь вводит `kubectl apply -f pod.yaml`. `kubectl` отправляет POST-запрос в формате JSON на `kube-apiserver`.
2.  `kube-apiserver` принимает запрос и последовательно проходит этапы **аутентификации, авторизации и проверки admission-контроллерами**.
3.  После успешной проверки `kube-apiserver` сохраняет объект Pod в хранилище **`etcd`**.
4.  `kube-apiserver` возвращает ответ пользователю, что объект создан.
5.  Тем временем, **`kube-scheduler`**, который постоянно "следит" за API, видит новый под без назначенного узла. Он выбирает подходящий узел и отправляет в `kube-apiserver` запрос на обновление пода (привязку к узлу).
6.  `kube-apiserver` снова проверяет запрос (не изменяет ли scheduler чужой объект?) и обновляет объект Pod в `etcd`.
7.  **`kubelet`** на выбранном узле, следящий за API, видит, что под назначен ему. Он запускает контейнер через container runtime (Docker, containerd) и начинает отправлять в `kube-apiserver` обновления статуса.

Подводя итог, `kube-apiserver` — это фундаментальный строительный блок. Он не только обслуживает все запросы к кластеру, обеспечивая безопасность через аутентификацию, авторизацию и admission control, но и выступает единственным звеном, связывающим хранилище состояния (`etcd`) со всеми остальными компонентами, реализуя таким образом основную управляющую логику Kubernetes.

`если говорить о том, как этот компонент представлен в kubernetes, то что это будет? в minikube я вижу только под kube-apiserver и кстати видимо все они расположены только на мастер ноде в одном экземпляре`

Да, вы абсолютно правильно подметили ключевой момент. Если говорить о том, как `kube-apiserver` представлен физически внутри работающего кластера Kubernetes, то ответ будет именно таким:

**Внутри Kubernetes компонент `kube-apiserver` представлен в виде статического пода (static pod).**

Вот подробности, которые объясняют, почему в Minikube (или в обычном кластере с одной мастер-нодой) вы видите только один под:

### 1. Это Статический Под
В кластере, созданном с помощью `kubeadm` (как Minikube или большинство "ручных" кластеров), компоненты control plane запускаются как **статические поды**.
*   **Где они лежат:** Манифесты (YAML-файлы) этих подов находятся на самой мастер-ноде в директории `/etc/kubernetes/manifests/`.
*   **Кто их запускает:** `kubelet`, работающий на мастер-ноде, постоянно сканирует эту папку. Как только он видит там файл (например, `kube-apiserver.yaml`), он говорит: "Ага, это под, который должен быть запущен на МОЕЙ ноде, независимо от остального кластера", и запускает его.
*   **Итог:** Именно поэтому вы выполняете `kubectl get pods -n kube-system` и видите там под `kube-apiserver-minikube` (или `kube-apiserver-<имя_вашей_ноды>`).

### 2. Расположение на Мастер-ноде
Вы абсолютно правы, что они расположены **только на мастер-ноде**.
*   В архитектуре Kubernetes компоненты control plane (`kube-apiserver`, `etcd`, `kube-scheduler`, `kube-controller-manager`) должны выполняться на мастер-узлах.
*   Воркер-узлы (те, где крутятся ваши приложения, например, `nginx`) не имеют доступа к этим манифестам и не запускают эти компоненты. Если `kubelet` на воркер-ноде попытается запустить `kube-apiserver`, он просто не сможет это сделать, потому что мастер-компонентам нужен доступ к сертификатам и специфичным конфигурациям, которых на воркер-ноде нет.

### 3. Один экземпляр (в Minikube)
*   **Почему один:** Minikube по умолчанию создает кластер с одной мастер-нодой. Для тестовой среды одного экземпляра достаточно. Это называется отсутствием отказоустойчивости (no High Availability), но для разработки это нормально.
*   **Как выглядит в продакшене (High Availability):**
    *   Если бы у вас был кластер с тремя мастер-нодами (например, `master-1`, `master-2`, `master-3`), то **на каждой** из этих трех нод лежал бы манифест `kube-apiserver.yaml`.
    *   Следовательно, `kubelet` на каждой мастер-ноде запустил бы свой экземпляр пода `kube-apiserver`.
    *   Таким образом, в неймспейсе `kube-system` у вас было бы **три пода** с именами `kube-apiserver-master-1`, `kube-apiserver-master-2`, `kube-apiserver-master-3`.
    *   Перед ними ставится балансировщик нагрузки (например, HAProxy или внутренний балансировщик в облаке), и все запросы от `kubectl` идут через него к этим трем апи-серверам.

Ваша картина мира верна на 100%:
1.  **"Это под?"** Да, это под, но особого типа — **статический под**, управляемый напрямую `kubelet`'ом мастер-ноды.
2.  **"Он на мастер-ноде?"** Да, только на мастер-нодах.
3.  **"В одном экземпляре?"** Да, потому что в Minikube одна мастер-нода. Если бы мастер-нод было три, было бы три пода `kube-apiserver`.

`почему это статический под, а не например deployment? что будет если я его удалю сейчас? как он пересоздастся, если вдруг его кто-то с правами удалит?`

Отличные вопросы! Давайте разберем их по порядку, так как они очень точно попадают в суть устройства Kubernetes.

### Почему статический под, а не Deployment?

Это фундаментальное архитектурное решение, основанное на принципе "курица или яйцо" (chicken-and-egg problem) .

*   **Зависимость от API:** `Deployment`, как и любой другой ресурс в Kubernetes (Pod, Service, ReplicaSet), управляется через **`kube-apiserver`**. Чтобы создать, обновить или следить за состоянием Deployment'а, контроллер-менеджеру (`kube-controller-manager`) нужно общаться с API-сервером .
*   **Порочный круг:** Представьте, что `kube-apiserver` еще не запущен или упал. Кто будет управлять его Deployment'ом? Контроллер-менеджер, которому для работы тоже нужен API-сервер. Получается замкнутый круг: для управления API-сервером через Deployment нужен работающий API-сервер.

**Решение — статические поды, управляемые Kubelet'ом:**
`kubelet` — это агент, который работает на **каждой** ноде, включая мастер-ноды. Он не зависит от Kubernetes API. Он запускается самой операционной системой (обычески как `systemd` служба) и его задача — следить за директорией манифестов на ноде (по умолчанию `/etc/kubernetes/manifests/`) .

Таким образом, `kubelet` запускает `kube-apiserver` (и другие компоненты control plane) **напрямую, без участия API**. Это разрывает круг зависимостей: `kubelet` (системная служба) запускает API-сервер, и только после этого становится доступным весь API Kubernetes для управления остальными приложениями .

### Что будет, если я удалю под `kube-apiserver`?

Если вы выполните команду `kubectl delete pod -n kube-system kube-apiserver-<имя_ноды>`, произойдет следующее:

1.  **Команда уходит в API:** `kubectl` отправляет запрос на удаление пода в `kube-apiserver`.
2.  **API-сервер получает запрос на собственное удаление:** Да, звучит странно, но это так. Работающий `kube-apiserver` получает запрос на удаление самого себя.
3.  **Запись об объекте Pod удаляется из etcd:** API-сервер удаляет объект `Pod` из хранилища `etcd`.
4.  **Kubelet "видит", что под пропал:** `kubelet` на мастер-ноде постоянно синхронизирует состояние кластера (то, что в `etcd`) с реальностью на ноде. Он замечает, что в API пода `kube-apiserver` больше нет.
5.  **Kubelet пересоздает под из манифеста:** Но `kubelet` по-прежнему видит файл `/etc/kubernetes/manifests/kube-apiserver.yaml` в своей директории. Его задача — гарантировать, что поды, описанные в этой директории, всегда запущены . Видя, что под пропал из API, он **немедленно создает его заново** на основе локального файла .

**Итог:** Под `kube-apiserver` исчезнет на секунду и тут же появится снова. Для кластера это будет кратковременный сбой (буквально на несколько секунд), но в целом он переживет это. Вы увидите, что счетчик `RESTARTS` в колонке увеличится на единицу. Это стандартный и безопасный способ "перезапустить" API-сервер, если это необходимо .

### Как он пересоздастся, если его кто-то удалит?

Механизм пересоздания мы уже описали выше. Главный страж здесь — **`kubelet`** .

1.  **Исходное событие:** Кто-то (или что-то) с правами отправляет запрос на удаление пода `kube-apiserver`.
2.  **Реакция Kubelet:**
    *   `kubelet` на мастер-ноде постоянно наблюдает за двумя вещами: за API-сервером и за своей локальной директорией манифестов.
    *   Он получает уведомление, что под `kube-apiserver` был удален из API.
    *   Он сверяется со своей локальной директорией `/etc/kubernetes/manifests/` и видит, что манифест `kube-apiserver.yaml` на месте.
3.  **Действие:** Для `kubelet` это сигнал "несоответствия". Локальная конфигурация требует, чтобы под был запущен, но в API его нет. Его работа — исправить это несоответствие .
4.  **Результат:** `kubelet` обращается к контейнерной среде выполнения (container runtime, например containerd) и дает команду снова создать контейнер(ы) для этого пода. Новый под `kube-apiserver` появляется в кластере.

### Как правильно управлять статическими подами?

Раз статические поды не подчиняются командам `kubectl delete`, для управления ими (например, для "настоящего" останова или изменения конфигурации) нужно работать напрямую с их манифестами на ноде .

| Действие | Команда (на мастер-ноде) | Пояснение |
| :--- | :--- | :--- |
| **Остановить под** | `sudo mv /etc/kubernetes/manifests/kube-apiserver.yaml ~/` | Переместите файл манифеста из директории `manifests`. `kubelet` увидит, что файла нет, и остановит под . |
| **Запустить под** | `sudo mv ~/kube-apiserver.yaml /etc/kubernetes/manifests/` | Верните файл обратно. `kubelet` увидит новый манифест и создаст под . |
| **Изменить параметры** | `sudo vi /etc/kubernetes/manifests/kube-apiserver.yaml` | Отредактируйте файл и сохраните его. `kubelet` автоматически заметит изменение и перезапустит под с новыми параметрами . |

### Резюме

*   **Статический под** — это единственный способ запустить API-сервер до того, как появится сам API .
*   **Kubelet** — это надзиратель, который гарантирует, что API-сервер всегда работает, пересоздавая его при удалении или падении .
*   **Файл манифеста** — это "источник истины" для статического пода. Управление подом сводится к управлению этим файлом на мастер-ноде .


`я удалил storage-provisioner под из kube-system и он почему-то заново не создался, почему?`

Отличный вопрос! Он показывает, что вы внимательно следите за поведением кластера. Ситуация, которую вы описали, абсолютно верна и является ключевым отличием в природе разных подов в пространстве `kube-system`.

**Краткий ответ:** Потому что `storage-provisioner` в Minikube — это не статический под, управляемый `kubelet`'ом напрямую, а обычный под, созданный **Deployment'ом** (или похожим контроллером). `kube-apiserver` — это статический под, поэтому он пересоздается `kubelet`'ом. `storage-provisioner` — это под, за жизненный цикл которого отвечает **контроллер Deployment'а**, работающий внутри `kube-controller-manager`.

### Глубинная причина: "Курица или яйцо" и иерархия управления

Давайте разберем это подробнее, опираясь на архитектуру, которую мы обсуждали ранее.

1.  **Статические поды (как `kube-apiserver`)**: Они существуют вне иерархии Kubernetes API. Их создает и пересоздает **`kubelet`**, читая файлы в директории `/etc/kubernetes/manifests/` на самой ноде . Это фундамент, на котором строится весь кластер. Если вы удалите такой под через API, `kubelet` увидит несоответствие между реальностью и файлом на диске и мгновенно пересоздаст под.

2.  **Обычные поды (как `storage-provisioner`)**: Они создаются через API и находятся под управлением **контроллеров** (ReplicaSet, Deployment, Job и т.д.). Их жизненный цикл описывается декларативным манифестом, который хранится в `etcd`. За то, чтобы фактическое состояние соответствовало этому манифесту, отвечает соответствующий контроллер из состава `kube-controller-manager` .

### Анатомия вашего эксперимента

Вот пошаговая схема того, что произошло, когда вы удалили под `storage-provisioner`:

1.  **Вы выполняете команду:** `kubectl delete pod -n kube-system storage-provisioner`
2.  **API-сервер принимает запрос:** Запрос уходит в `kube-apiserver`, он аутентифицирует и авторизует вас.
3.  **API-сервер удаляет объект Pod из `etcd`:** Самое главное. Объект `Pod` (запись о том, что под существовал) стирается из хранилища `etcd`.
4.  **API-сервер сообщает об удалении:** Он уведомляет всех, кто "слушает" (вотчивает) события об удалении подов. Одним из таких слушателей является **контроллер Deployment'а**.
5.  **Контроллер Deployment'а реагирует:** Контроллер Deployment'а, следящий за состоянием, видит: "В манифесте Deployment'а написано, что должно быть 1 реплика пода `storage-provisioner`, а в реальности (в `etcd`) их 0". Это несоответствие — его работа.
6.  **Контроллер создает новый под:** Контроллер Deployment'а отправляет в `kube-apiserver` команду на создание нового пода взамен удаленного.
7.  **API-сервер сохраняет новый под:** `kube-apiserver` создает запись о новом поде в `etcd`.
8.  **Kubelet запускает под:** `kubelet` на соответствующей ноде замечает, что появилось задание запустить новый под, и выполняет его.

**Почему же он не создался?** Судя по вашему описанию, скорее всего, шаги 5-8 не выполнились. Это могло произойти по двум причинам:

*   **Контроллер Deployment'а не работает или "не видит" это событие.** Маловероятно в здоровом кластере, но если бы `kube-controller-manager` был перегружен или имел проблемы, он мог не успеть обработать событие удаления.
*   **Deployment или его ReplicaSet были удалены.** Это самая вероятная причина. Если кто-то (или что-то) до этого удалил сам ресурс `Deployment` (или `ReplicaSet`), отвечающий за `storage-provisioner`, то после удаления пода контроллеру будет просто **нечего восстанавливать**. Декларативное состояние (манифест) потеряно.

### Вывод

Ваш эксперимент блестяще продемонстрировал разницу между двумя уровнями управления в Kubernetes:
*   **Уровень 1 (Инфраструктурный):** Статические поды, управляемые `kubelet`'ом. Они живут, пока есть файл на диске ноды.
*   **Уровень 2 (Уровень приложений):** Обычные поды, управляемые контроллерами (Deployment, DaemonSet и т.д.). Они живут, пока существует их контроллер в `etcd`.

`kube-apiserver` — это уровень 1. `storage-provisioner` — это уровень 2. Поэтому они и ведут себя по-разному.
